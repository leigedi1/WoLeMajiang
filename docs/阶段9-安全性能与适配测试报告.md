## 1. 测试环境与方法

| 项目 | 值 |
| --- | --- |
| 压测对象 | `server/cmd/server`（与线上同二进制），临时实例 `127.0.0.1:18791`，独立 SQLite（`/root/mj-stress/stress.db`） |
| 压测工具 | `server/cmd/stress`（本仓库新增，纯 Go，仅依赖 stdlib + gorilla/websocket） |
| 采集脚本 | `server/scripts/run-stress.sh`（启动实例 → 压测 → 每 2s 采样 `/proc/<pid>/stat`、`VmRSS`、`loadavg`） |
| 服务器 | 阿里云生产机：2 vCPU / 1676 MB（提示词要求"1 核 1GB 参考环境"，本机 CPU 略多、内存略多；生产实例同时在线，未停服） |
| 拓扑 | 全部走 loopback（`http://127.0.0.1:18791`），无公网/Caddy/TLS 干扰 |

复现命令：

```bash
# 本机
cd server
$env:Path='D:\SOFT\go\bin;'+$env:Path
go run ./cmd/stress -mode abuse  -base http://127.0.0.1:8790
go run ./cmd/stress -mode normal -base http://127.0.0.1:8790 -rooms 3 -players 4 -timeout 240s

# 服务器（专用实例 + 资源采样；脚本随仓库提供）
bash server/scripts/run-stress.sh
```

压测客户端行为：HTTP 建游客 → WS `guest.hello` → 房主 `room.create`、其余 `room.join` → 满座 `game.start` →
每个客户端按**自己的私有视图**自动出牌（`hu` → `discard(drawn|手牌末张)` → `draw` → `pass`），
每秒 `ping` 一次测 RTT；对局消息节流 120ms/条（模拟人类反应，避免压测器自己打满限流桶）。

## 2. 资源实测（3 房 × 4 人 = 12 连接，240s）

| 指标 | 实测值 |
| --- | --- |
| 动作总数 | 615（每房约 0.85 动作/秒） |
| 消息 | 入 3198 / 出 3510 |
| 错误 | 0（无 `rate_limited`、无断线、无 5xx） |
| CPU（进程） | 均值 ≈ 0.5%，峰值 11.5%（启动瞬间），`load1` 峰值 0.07 |
| RSS | 启动 15.0 MB → 稳定 19.4–20.8 MB（240s 内仅 +0.5 MB，无持续增长趋势） |
| RTT（ping 回显） | p50 0.70 ms / p95 120 ms / max 121 ms（p95 由**压测端 120ms 节流**让 ping 排队所致，非网络/服务端延迟） |
| 动作延迟 `actLag`（视图到达 → 发动作） | p50 0 ms / p95 35.7 ms（节流重试窗口） |
| 广播延迟 `sendGap`（发动作 → 收到下一条对局事件） | p50 0.59 ms / p95 1.06 ms / max 6.0 ms |

对照：**单机本机**单房 4 人（120s）= 205 动作（3.4 动作/秒）；远端 12 连接时为 0.85 动作/秒/房。

### 结论

- **CPU / 内存远未成为瓶颈**：12 连接对局时进程 CPU < 1%、RSS ≈ 20 MB，距 1 核 1 GB 上限极远。
- 单步延迟极低（动作视图 p50 < 1 ms，广播 p50 0.6 ms），说明是**回合节奏**而非服务器处理能力限制吞吐：
  每个回合需要 4–5 次客户端往返（摸牌/出牌 + 3 个响应者 `pass`），压测端又节流 120 ms/条。
- 12 连接 240 s 内未跑到结算（`gamesFinished=0`），按当前节奏 4 人整局约 8–10 分钟；
  本机单房约 3–4 分钟。**未达标项**：未在真 1 核 1 GB、未跑到一局结束，需补长跑。

## 3. 异常输入 / 滥用探测（`-mode abuse`，8/8 通过）

| 探测 | 服务端实际行为 | 结果 |
| --- | --- | --- |
| 坏 token 握手 | `error{code=auth_failed}`，随后断开 | ✅ |
| 首帧不是 `guest.hello` | `error{code=expected_hello}` | ✅ |
| 2 MB 超长帧（上限 64 KB） | 连接被强制关闭（`SetReadLimit`） | ✅ |
| 非法 JSON | `error{code=bad_message}`，连接保留 | ✅ |
| 1 秒 60 条洪泛 | `error{code=rate_limited}` + 优雅关闭 | ✅ |
| 无效房间码 | `error{code=room_not_found}` | ✅ |
| 超出 `MaxOnlineRooms=3` 建第 4 房 | `error{code=max_online_rooms}` | ✅ |
| 无效邀请令牌 | `error{code=room_not_found}` | ✅ |

已具备的防线（代码位置）：

- 帧上限 `ws.go:186` `SetReadLimit(64KB)`；HTTP body `MaxBytesReader(1MB)`。
- 每连接令牌桶 `ws.go:174`（10 条/秒，burst 30），超限告警并关闭。
- 读空闲 90s / 写 10s 超时；`protocol.Decode` 校验长度、JSON、版本、type。
- SQLite `journal_mode=WAL` + `busy_timeout=5000`（单连接串行，避免写阻塞）。
- 身份：游客 token 哈希存储；房间密码只存哈希、协议仅回 `hasPassword`；邀请令牌只回一次明文、库存哈希。
- 视图投影：`ViewFor(seat)` 只含本人手牌，他人仅 `othersHandCounts`（结构上无法读到隐藏牌）。
- WS 来源：在线通道读 `MAJIANG_ALLOWED_ORIGINS`；信令通道三级放行（无 Origin / 同源 / 白名单 / 局域网前缀）。

## 4. 本次修改

1. **新增安全响应头**（`server/internal/httpapi/server.go` `withMiddleware`）：
   `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`、
   `Permissions-Policy: camera=(), microphone=(), geolocation=()`。
   （线上 Caddy 之前未下发任何安全头，可被 MIME 嗅探 / iframe 嵌入。）
2. **前端小屏/横屏适配**（`web/src/components/MahjongTable.vue`）：
   桌面仍为 `min-height: 540px`；改为 `min(540px, calc(100dvh - 8rem))`，
   并在 `@media (max-height: 640px)`（手机横屏）下取消最小高度、限制 `max-height` 并允许内部滚动；
   触控设备加 `touch-action: manipulation`（去掉双击缩放与点击延迟）。
   已有动效开关（`ThemeSwitcher` 的「动效: 开/关」）满足"动画可降级/关闭"。
3. **XSS/CSRF 复核**：`web/src` 全量 grep 无 `v-html`（无 HTML 注入点）；所有用户输入走 Vue 文本插值；
   鉴权仅依赖 WS 首帧 token + HTTP 游客接口，无 Cookie 会话 ⇒ 无传统 CSRF 面（接口均校验 token）。

| 手机真机未验证 | 仅代码级适配，未在真机横屏/触控操作 | 用真实手机走一遍建房/开局/出牌 |

## 6. 优化建议（按收益排序）

1. **响应窗口聚合**：出牌后 3 个响应者各自 `pass` 会产生 3 次往返；服务端可对"无动作可做"的座位直接视为 pass（仅保留可碰/杠/和的座位等待），可显著缩短每回合耗时。
2. **广播合并**：当前每个动作向全房广播一次；同一 tick 内多次状态变化可合并为一次投影下发（前端已按 `seq` 幂等）。
3. **压测端并发**：提高 `-players` 与节流参数，补跑整局与断线恢复，形成容量基线（每房 CPU/RSS 常数）。
